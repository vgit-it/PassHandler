# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Vault — a personal KeePass-compatible (`.kdbx`) password manager for Windows and Android, built with Tauri 2. The vault format and crypto come entirely from [`kdbxweb`](https://github.com/keeweb/kdbxweb); this repo never implements its own crypto. Sync is encrypted-blob storage in a hidden, app-only Google Drive folder — Google never sees a key or plaintext. Offline-first: reading/editing never requires network.

Built for one person (later a couple more), each with a fully independent vault. No accounts, no server, no shared backend, no telemetry, no remote fonts/assets/update checks. The webview CSP has no remote origins.

## Commands

```bash
npm install

npm run dev                    # Vite dev server only (rarely useful alone)
npm run tauri dev              # Windows app, hot-reloading
npm run tauri android init     # once, or after deleting src-tauri/gen/android
npm run android:sync-ime       # after every android init — see below
npm run tauri android dev      # Android app

npm run typecheck              # tsc --noEmit
npm run lint                   # eslint .
npm run test                   # vitest run (all tests, Node environment)
npm run test:watch             # vitest watch mode
npm run build                  # typecheck + vite build

# Single test file / test name:
npx vitest run tests/sync.test.ts
npx vitest run -t "test name substring"

# Rust side (src-tauri):
cargo check --manifest-path src-tauri/Cargo.toml --all-targets
cargo test --manifest-path src-tauri/Cargo.toml --lib
```

CI (`.github/workflows/ci.yml`) runs, as separate jobs: a fast Linux job (typecheck, lint, `npm test`, frontend build, `cargo check`, `cargo test`), a Windows job that produces the real NSIS/MSI installers, and an Android job that runs `npx tauri android init`, then `npm run android:sync-ime`, then `npx tauri android build --debug --apk --split-per-abi`. `src-tauri/gen/` itself is generated and gitignored, regenerated by `tauri android init` — but it is not exclusively Tauri boilerplate: every hand-authored Android file — the custom IME (below), this app's `MainActivity.kt` (replacing the stub `android init` generates), and its theme resources (`colors.xml`, both `themes.xml`) — lives in tracked `src-tauri/android-ime/`, copied into `gen/android` by that sync step (`scripts/sync-android-ime.js`). Never hand-edit anything under `gen/` directly — edit the tracked copy and re-sync; a new hand-edited Android file goes into `src-tauri/android-ime/` and the sync script in the same change.

Google Drive sync is optional at build time: with no `VITE_GOOGLE_CLIENT_ID_*` set in `.env` (see `.env.example` and [docs/google-oauth-setup.md](docs/google-oauth-setup.md)), the app builds and runs local-only and Settings reports Drive as unconfigured. This path is what CI's Android job exercises, since it has no OAuth secrets.

## Architecture

```
React UI          src/ui, src/app
      ↓
Vault service     src/vault      pure TS over kdbxweb — unlock, CRUD, merge
Sync engine       src/sync       pure TS state machine
      ↓
Platform ports    src/platform   interfaces (ports.ts) + the one Tauri impl (tauri.ts)
      ↓
Rust / Kotlin     src-tauri      file I/O, OAuth, Drive HTTP, secure storage, biometrics
```

**The dependency rule is enforced, not just conventional.** `src/vault`, `src/crypto` and `src/sync` must never import `@tauri-apps/*` or `src/platform/tauri`; `eslint.config.js` makes this a lint error (`no-restricted-imports`) and additionally bans `console.*` in those three directories (secrets pass through them — nothing may log, including in catch blocks). This is what lets the same vault/sync code run in the Windows webview, the Android webview, and under plain Node in `vitest` — which is how two-device sync scenarios are tested without two devices (`tests/support/fakeDrive.ts` stands in for Drive with real revision semantics).

- **`src/platform/ports.ts`** — the `Platform` interface every screen depends on (never a concrete Tauri call directly from UI code). Covers local vault I/O, settings, Drive, clipboard, biometrics, favicon fetch, screen-capture blocking, and the Windows manual-fill hotkey bridge (`typeText`/`pressTab`/`onEnterPickMode`).
- **`src/app/store.tsx`** — the one `AppProvider`/`useApp()` context holding all app state and actions (unlock, CRUD, sync, settings, Drive connect, biometrics, export/restore). The decrypted `Vault` and any in-progress account-creation draft are kept in `useRef`, deliberately never in React state, so they never land in a DevTools snapshot. This file also installs `window.__vaultFill` / `window.__vaultCreate` — the JS bridge Android's custom IME (`VaultIme.kt`, native Kotlin) calls via `evaluateJavascript` for manual fill and streamlined account creation. See "Bridge surfaces" below.
- **`src/vault/vault.ts`** — the `Vault` class wrapping `kdbxweb`: unlock, CRUD, field read, merge. `login`-type entries stay on KeePass's standard Title/UserName/Password/URL/Notes fields for KeePassXC interop; every other entry type uses a generic `ph:f:`/`ph:c:` custom-field scheme. `src/vault/entryTypes.ts` is the entry-type registry — the single source of truth for what fields each type has, consumed by the type picker, the editor, and (via the bridge) the Android quick-fill UI.
- **`src/sync/syncEngine.ts`** — the sync state machine. Google Drive has no conditional write, so instead of locking, losing the upload race is made harmless: read `headRevisionId`, upload, re-read and confirm it's still the file just written; if not, mark dirty and merge next cycle rather than overwrite. KeePass UUIDs + per-entry mtimes mean a conflict resolved one cycle late still loses nothing. Read the file's own doc comment before touching this — it explains the invariants ("never silently pick a winner", "never delete local because remote is missing") in more depth than is worth repeating here.
- **`src-tauri/src/`** — thin plumbing only; no vault parsing or decryption ever happens on the Rust side (`lib.rs`'s module doc says this explicitly). `drive.rs` (Drive HTTP), `oauth.rs` (PKCE flow, desktop loopback listener vs. Android custom-scheme redirect), `vault_file.rs` (local file + rolling backup), `prefs.rs` (settings/sync-state persistence), `favicon.rs` (direct-from-site fetch, never a third-party icon service), `fill.rs` (Windows-only global hotkey + synthetic keystroke typing for manual fill).
- **`src-tauri/plugins/tauri-plugin-vault/`** — the custom Tauri plugin for what has no cross-platform library: biometric-gated secure storage, clipboard-clear-if-matches, screen-capture blocking. `android/src/main/java/VaultPlugin.kt` is the Kotlin side (Keystore-backed `EncryptedSharedPreferences`, `BiometricPrompt`, `FLAG_SECURE`); `src/desktop.rs` is the Windows side (Credential Manager, Windows Hello via `IUserConsentVerifierInterop`).

### Why Tauri, not React Native

`kdbxweb` needs WebCrypto. Tauri renders in the system webview on both platforms, where WebCrypto is native, so the vault logic is genuinely one shared implementation. React Native has no native WebCrypto and would need a polyfill — not acceptable for a password manager's crypto path.

### Bridge surfaces (Android manual fill / account creation)

Android has no Autofill Framework integration; instead a custom IME (`VaultIme.kt` + `WebViewBridge.kt`, native Kotlin, plus `VaultKeyboardView.kt` for its own view code) talks to the already-running webview via `evaluateJavascript`, calling `window.__vaultFill` and `window.__vaultCreate` (installed by `src/app/store.tsx`, only while `phase === 'unlocked'` — that's what makes the bridge fail closed with no native-side lock-state awareness needed). Because these bridge calls are the *only* code path that still runs while the page is fully backgrounded, every bridge function calls `enforceAutoLockOnBridgeCall` first — the one place idle-timeout enforcement is reachable for an IME-only session. Edit these files under `src-tauri/android-ime/` (tracked), never under `src-tauri/gen/android/` directly — see the Commands section above and `scripts/sync-android-ime.js`'s own doc comment. See [docs/MANUAL-FILL-DESIGN.md](docs/MANUAL-FILL-DESIGN.md) and [docs/ACCOUNT-CREATION-DESIGN.md](docs/ACCOUNT-CREATION-DESIGN.md) before touching any of this — both have a "gotchas found after shipping" section worth reading first.

## Design docs

`docs/*-DESIGN.md` and a few root-of-`docs` `.md` files capture non-obvious decisions for specific features (export/restore, manual fill, account creation, quick-fill ranking, entry types, date-renewal fields, email suggestions, the visual-language spec). When working on one of these areas, read the matching doc first — the reasoning behind edge cases usually lives there, not in code comments.

**The vault visual-language migration is partial, not app-wide.** `docs/vault-visual-language-spec.md` defines a full replacement design system (flat "physical vault" shelves/pegs/planes, `--vault-*` tokens); `docs/vault-visual-overhaul-plan.md` tracks what's actually shipped against it — currently phases 1–8 (tokens, the entry shelf/peg, the search shelf, the tab channel + "+", section rails, the detail-view "deposit box" container transform (plan doc §6g), and the doors/two-stage-unlock/auto-lock creep, plus the unlock reveal inside the vault as the doors part — plan doc §6h) plus a fix for a gap every one of those phases shared: none of them ever built the actual vault **frame** (spec §1's bezeled box with corner bolts) — see the plan doc's §6a. `EntryList.tsx`/`BottomTabBar.tsx`/`VaultScreen.tsx`/`EntryDetail.tsx`/`PickEntryDetail.tsx`/`App.tsx`/`VaultDoors.tsx`/`ShelfOriginPanel.tsx`/`VaultFrame.tsx` are the touched files. Settings and the entry editor are still on the older `ink-*`/card-based system (`--vault-*` and `ink-*` tokens are deliberately namespaced so both can coexist file-by-file during the migration). `Unlock.tsx` is deliberately NOT wrapped in the vault frame — it has its own separate, pre-existing design, and the doors are decorative chrome that must never sit as an opaque layer over its actual password field. Don't assume a screen uses vault tokens just because the spec exists — check the plan doc's own scope map first. **Phase 9 (the 3D Settings turn) is permanently skipped for this app**, not merely deferred — Settings stays on its current visual treatment for good.

## Conventions worth knowing

- Path alias `@/*` → `src/*` (see `tsconfig.json` / `vite.config.ts`).
- `Math.random` is lint-banned everywhere (`no-restricted-properties`) — use `crypto.getRandomValues` (`src/crypto/random.ts`) for anything password-generation-adjacent.
- Nothing is fetched at runtime: no CDN, no remote fonts, no remote wasm. `hash-wasm`'s Argon2 WASM ships inlined as base64 in the JS bundle (`assetsInlineLimit: 0` in `vite.config.ts` is *not* about that — check the config's own comments before assuming otherwise).
- `@xmldom/xmldom` is aliased to `src/platform/xmldomShim.ts` in `vite.config.ts`: `kdbxweb` eagerly imports it, but that import alone crashes under `tauri.conf.json`'s `security.freezePrototype`; the webview's native `DOMParser`/`XMLSerializer` is used instead.
- Tests run under Node (`vitest.config.ts`, `environment: 'node'`) — the vault/sync/crypto layers work there unmodified because they never touch platform APIs. Argon2 test timeouts are set high (60s) for a cold WASM compile.
