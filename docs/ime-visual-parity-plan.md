# IME visual parity — plan

**Status: implemented in `src-tauri/android-ime/` (tracked source),
synced into `gen/android`. Not yet real-build-verified** — this sandbox has
no Android SDK/Kotlin compiler; verification so far is brace/paren/bracket
balance (clean) and manual re-reading, the same substitute every other
Kotlin change in this project has used. A real Android Studio build and a
look at `VaultImePreviewActivity` are what's actually left — see
"Implementation notes" below for what to specifically eyeball first.

## Why this exists

`docs/vault-visual-overhaul-plan.md` (the web app's own redesign) explicitly
scoped the IME out: "the IME is a separate native Kotlin UI with its own
recently-built visual language... untouched by this plan." That was correct
when written. It's no longer the intended end state — the IME is now meant
to look like the same app, not a differently-themed companion to it.

## Reference: **the Android-rendered main app**, not the web app in general

Everything in this document targets what actually ships on Android today —
`Unlock.tsx`/`VaultScreen.tsx`/`EntryList.tsx`/`VaultDoors.tsx`/
`BottomTabBar.tsx`/`EntryDetail.tsx`/`Settings.tsx`'s own `isAndroid`
branches specifically, not their Windows branches, and not
`docs/vault-visual-language-spec.md`'s original `--vault-*` token values in
the abstract. That distinction matters and is the reason this document
exists rather than just finishing the migration `ime-ux-redesign-proposal.md`
already proposed once (see "Supersedes" below): **the Android app has
itself drifted from those original tokens**, per that spec's own
status-correction note ("Android has since diverged from several of the
shared recipes... in a later Figma-parity pass not reflected in this
spec"). A handful of `--vault-*` tokens still happen to match (noted below,
constant by constant); most of what the Android app actually paints today
is a newer, separate set of literal hex values that were never folded back
into the token system. Chasing the token file would have reproduced a
theme that doesn't exist on screen. Every value below was re-verified
directly against the current Android-branch source, not copied from the
spec or from the prior (stale) proposal.

## Source tracking (already fixed, prerequisite to everything below)

`src-tauri/gen/android/` is gitignored, regenerated by `tauri android init`.
The source of truth for every hand-authored Android file is tracked
`src-tauri/android-ime/`; `npm run android:sync-ime`
(`scripts/sync-android-ime.js`) copies it into `gen/android` and patches in
its manifest entries, idempotently, and CI runs it between `android init`
and the build. The full list of what it carries is in
`MANUAL-FILL-DESIGN.md`'s "Source tracking" section. **Edit
`src-tauri/android-ime/`, never `src-tauri/gen/android/` directly.**

## The current IME: three palettes, flat Views, no shared chrome system

- **Shared chrome** (top bar, search, results, detail view, keypad):
  `VaultKeyboardView.kt`'s companion object, a self-contained blue-navy
  palette — see the table below.
- **Create-flow panel** (`buildCreatePanel`/`buildDraftFieldRow`/
  `buildPasswordOptionsPanel`, `CREATE_*` constants): a separate, deliberate
  warm dark-brown/coral palette, pixel-sampled from a reference screenshot
  (no source file) after two earlier guesses (no-accent, then the reference
  project's blue `EntryEditor.tsx`) both turned out wrong. Scoped narrow on
  purpose — `buildDetailView`/`smallActionButton` are unaffected.
- **Avatar colors** (`AVATAR_COLORS`, `buildAvatar`): six Tailwind
  rose/amber/lime/teal/sky/violet hues at ~20% alpha, an approximation of
  the web app's own peg color — except the web component that inspired it
  was since replaced (see "Supersedes" above).

Everything is built with classic Android Views —
`LinearLayout`/`FrameLayout`/`TextView`/`Button`, constructed and
`addView`'d by hand in one 2652-line file. No XML layouts, no Compose (zero
`@Composable`, zero Compose Gradle dependency). Shapes come from three
helpers (`filledRoundedRect`/`strokedRoundedRect`/`filledOval`) called with
a radius per call site — there is no shared "this is what a button looks
like" recipe the way the web app's gradient-pill class is reused everywhere
it appears. Typography is plain system `Typeface` (Roboto), not the web
app's bundled Inter/JetBrains Mono.

## Decision: full chrome match, not just a color swap

Confirmed with the requester: this pass rebuilds button/panel *chrome*
(gradient fills, matching corner radii) to actually look like the web app's
components, not only share their hex values. Concretely, every solid-filled
button (`filledRoundedRect` call sites in the shared chrome and — see next
section — the create panel too) becomes a two-stop vertical gradient with a
1px border and soft shadow, mirroring the web app's own recipe exactly:

```
background: linear-gradient(to bottom, #3f454a, #32373d)
border: 1px solid #565656
shadow: 0 0 4.3px rgba(0,0,0,.25)
```

(`Unlock.tsx:241`, reused verbatim at `Unlock.tsx:465`, `:494`,
`VaultScreen.tsx:729`, `:765` — this exact recipe, not an approximation, is
already used for every gradient-pill button across the real Android app:
Lock, Settings, Enter/submit, and the fingerprint-unlock button.) Android's
`GradientDrawable` (`orientation = TOP_BOTTOM`, two colors, `setStroke`)
is the direct equivalent — no new dependency needed, same
`filledRoundedRect`-style helper, extended rather than replaced.

## Target values — shared chrome

Re-verified against live Android-branch source, not the spec file. "No
change" means the current IME constant already happens to equal the real
target — confirmed, not assumed, and worth knowing so the implementation
pass doesn't spend effort "fixing" something already correct.

| Constant | Current (old/ink) | Target | Source (Android-branch) |
|---|---|---|---|

| `SECONDARY` | `#1A2D44` | *(retired — see below)* | was "the neutral fill every key uses"; every button-shaped key becomes a gradient-pill per the chrome decision above, so there's no flat "secondary fill" left to map it to |
| `SECONDARY_FOREGROUND` | `#B8CEDF` | `#d6e4ef` | ubiquitous across every Android screen — `EntryList.tsx`, `Unlock.tsx`, `EntryDetail.tsx`, `Settings.tsx`, all cite this exact hex directly |

cleanly — there are two border tones now (`#4d5761` general, `#565656`

force a single `BORDER` to do both jobs.

## Target values — create-flow panel (stays coral, gets the new chrome)

Confirmed with the requester: **not** dropped to the neutral palette above.
The account-creation panel keeps its distinct warm/coral identity — that
was a deliberate, sampled design choice (see "current IME" above), not a
leftover — but its buttons move onto the same gradient-pill recipe as
everywhere else, recolored in the coral family instead of the neutral one.

The existing `CREATE_*` hex values (`CREATE_BG #241A16`, `CREATE_BORDER
#4A352D`, `CREATE_ACCENT #E0A087`, `CREATE_ACCENT_TEXT #241A16`,
`CREATE_MUTED #A8887C`, `CREATE_CHEVRON #A7A3A2`, `CREATE_FG #FFFFFF`) are
kept as the base identity — no reason to re-sample a palette that was
already deliberately chosen and is still correct as a *hue family*. What
changes is structural, not chromatic: `createPillButton`
(`CREATE_ACCENT`-filled, currently a flat `filledRoundedRect`) and the
smaller `CREATE_ACCENT`-stroked button become two-stop coral gradients with
a border and shadow, mirroring the neutral recipe's shape exactly —
lighter-to-darker coral (e.g. a lightened/darkened pair derived from
`CREATE_ACCENT #E0A087`) in place of `#3f454a`→`#32373d`, border derived
from `CREATE_BORDER` in place of `#565656`. Exact gradient stops are an
implementation detail to pick and eyeball via `VaultImePreviewActivity`
(the existing debug harness for exactly this), not something to freeze here
in the abstract.

## Corner radii

| Use | Current (IME, dp) | Target |
|---|---|---|
| Buttons (all gradient-pill buttons, both palettes) | 6 (keypad keys), 8 (small action chips), 12/18 (create panel) — inconsistent | 5px, matching every gradient-pill button on Android (`rounded-[5px]`, `Unlock.tsx:241`, `VaultScreen.tsx:729`) |
| Fields / result rows / cards | 8 | 10px, matching `EntryList.tsx`'s search field and `EntrySiteIcon`'s icon box (`rounded-[10px]`), `Unlock.tsx`'s password field (`rounded-[10px]`) |
| Modal-scale containers (if any apply — none currently do; noted for completeness) | — | 20px, matching `Unlock.tsx`'s login-panel modal (`rounded-[20px]`) |

The 2dp handle-grip and the search-box pill's existing 20dp are unrelated
decorative/legacy uses — not part of this button/field/card system, left
alone unless implementation finds a reason to fold them in.

## Avatar / peg colors

`AVATAR_COLORS`'s six Tailwind hues approximate a component that no longer
exists. The real current mechanism, `EntryList.tsx`'s `pegColor`/
`PEG_COLORS`/`PEG_FOREGROUND`:

```
PEG_COLORS = [
  '#c9835f', // terracotta
  '#c7a23f', // brass
  '#8caf5f', // moss
  '#5fac93', // teal-green
  '#9a8fc9', // steel violet
  '#c97ba3', // rose plum
  '#9aa3ad', // slate
  '#c9955f', // ochre amber
]
PEG_FOREGROUND = '#0a0d10'
hash = (hash * 31 + charCode) — same per-character accumulation, just JS's
  `>>> 0` vs. Kotlin's `Int` overflow, so the two hashes won't be
  bit-for-bit identical — cosmetic, not a correctness issue (same note the
  in-code comment already carries).
```

Target: replace `AVATAR_COLORS`' six entries with these eight (text color
becomes the single `PEG_FOREGROUND`, not per-entry — the current
`Pair<Int,Int>` scheme with a separate light text tone per hue has no
equivalent in the web version, which always draws `PEG_FOREGROUND` on top
regardless of the background hue).

## Typography and icons — flagged, not resolved here

- **Fonts**: the web app bundles real Inter/JetBrains Mono via
  `@fontsource/*` npm packages (self-hosted `.woff2`, no network fetch —
  confirmed present under `node_modules/@fontsource/inter`,
  `@fontsource/jetbrains-mono`). Bundling the actual font files into
  `res/font/` and switching `Typeface` calls to them is possible, not just
  aspirational — but it's a real, separate decision (APK size, a `res/font/`
  XML family definition, `Typeface.createFromAsset`/`ResourcesCompat`
  wiring) that this document flags rather than schedules. Until decided,
  the IME keeps system Roboto/monospace.
- **Icons**: only `ic_lock`/`ic_globe`/`ic_vault_logo` were transcribed
  when this was written (`ic_home_logo` was added later, item 10 below).
  The detail view and top bar reference several more concepts
  (settings, edit, trash, eye/reveal, fingerprint) that may currently be
  drawn some other way (emoji, text glyph, or simply absent) — needs a
  screen-by-screen audit against `src/ui/components/icons.tsx` during
  implementation, not assumed complete here.

## Not in scope

- The Google Drive OAuth redirect intent-filter (`docs/google-oauth-setup.md`)
  — per-developer value, stays a manual step.
- `SECONDARY`'s literal retirement doesn't mean deleting the constant
  outright sight-unseen — implementation should grep every remaining call
  site first in case one turns out not to be a "key," same caution that
  caught `BORDER`'s two-tone split above.
- Windows: the IME is Android-only; nothing here touches the Windows build.
