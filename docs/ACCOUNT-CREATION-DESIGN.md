# Streamlined account creation — design

The feature: when you're creating a new account on a website or in an app,
Vault should do almost all of the work — generate the password, type
it in, and save a matching vault entry — without you having to leave
whatever you're signing up for to go build that entry by hand afterwards.

**Status:** built end to end, with one now-fixed regression worth knowing
about. The vault-layer foundation (the review flag, `EntryList`'s "Review"
section) is verified — typecheck/lint/test/build all pass, including tests
in `tests/vault.test.ts` and `tests/fieldKeys.test.ts`.

**Regression, found and fixed:** despite this doc's own earlier claim that
the JS/webview bridge was "likewise verified" after "Revision: any entry
type..."/"Revision: generator options..." below, `store.tsx` had silently
drifted back to a fixed Login-only draft shape (`DraftLoginState`, flat
`username`/`email`/`password`/`url`/`notes` properties, no `type`, no
`fields`) — while the Kotlin side had already moved on to the generic
`type` + `fields` shape described below. `getDraft()` kept returning the old
flat object, which has no `fields` key at all, so `WebViewBridge.parseDraft`
always parsed an empty field list — the creation panel opened but rendered
no fields, for any draft, of any type. This is exactly the kind of drift
`typecheck`/`lint`/`test`/`build` can't catch: the stale JS shape was
internally self-consistent on its own, and the Kotlin side isn't compiled
in this project's sandbox at all (see below), so nothing here ever
cross-checked the two sides against each other. Fixed by moving the draft's
pure logic (field-def-per-type, wire-snapshot building, `EntryInput`
construction) into `vault/accountCreationDraft.ts`, dependency-free the same
way `entryTypes.ts`/`emailSuggestions.ts` are, with real coverage in
`tests/accountCreationDraft.test.ts` — including an assertion that every
registered entry type produces a non-empty draft field list, which is
exactly the check that would have caught this before it shipped.
`store.tsx` now just wires that module's functions into
`window.__vaultCreate`.

**Second Kotlin regression, found later and now rebuilt (see the final
revision, not yet compiler-verified):** the IME's creation panel had (a) sent "Pick from Vault" on
the Email field into the ordinary entry search flow (`startPickingForDraftField`)
instead of offering already-saved emails, and (b) had no generator UI at
all — "Generate" just typed a password with the default options. Both are
described as *built* in the revisions below ("...a narrower/dropdown Pick
from Vault", "...generator options"); the Kotlin for both had gone missing, while the
JS/bridge side (`listKnownEmails`, `setDraftPasswordOptions`,
`DraftSnapshot.passwordOptions`) is intact. "Revision: inline email list and
the full generator panel" at the end of this document is the spec they were
rebuilt from, and supersedes those two revisions' Kotlin-side specifics
(`PopupMenu`, "nothing collapses the panel").

**Known gap, not restored, found while fixing the above (the Options-panel
half of this is now rebuilt — see the final revision; the Type row and the
Show/Hide pill below are still missing):** the same
intervening regression also stripped `VaultKeyboardView.kt`'s
"Type" row (`buildDraftTypeRow` — the UI that would call the now-working
`listEntryTypes`/`setDraftType`) and its password-generator Options panel
(`buildPasswordOptionsPanel`, the UI that would call
`setDraftPasswordOptions`) entirely. The JS/TS side now implements the full
contract the Kotlin side expects — including these two — so a Kotlin fix
can wire them back in without touching `store.tsx` again. Until the Type row
is wired back in, the IME's creation panel always defaults to (and can't
leave) Login. (The Options panel has since been rebuilt.) Every other draft field for a Login entry
(Username/Email/Password/URL/Notes) renders and commits correctly.

The Kotlin/Android side —
`WebViewBridge.kt`'s draft functions, `VaultIme.kt`'s
`EditorInfo`-based quiet-bias detection, and `VaultKeyboardView.kt`'s
in-keyboard creation panel, including the redesigned "+" key — is written
but **not compiler-verified**: this sandbox has no Android/Kotlin build
toolchain, so it was checked by brace/paren balance-counting and staleness
greps only, the same caveat every other Kotlin change in this project has
carried. A real build (Android Studio or `gradlew assembleDebug`) is the
first thing to run against it. Also worth knowing: `WebViewBridge.kt`,
`VaultKeyboardView.kt`, `VaultIme.kt`, and `VaultImePreviewActivity.kt`
live in tracked `src-tauri/android-ime/`, not in the gitignored
`src-tauri/gen/android/` (regenerated by `tauri android init`): edit the
tracked copy, then run `npm run android:sync-ime` to copy it into
`gen/android` (see `MANUAL-FILL-DESIGN.md`'s "Source tracking"). This document
exists so that work doesn't start from scratch, and so the several decisions
behind it (made across a few rounds of back-and-forth) don't have to be
re-derived.

Scope: Android only. Originally Login-type entries only; broadened to
every registered entry type by "Revision: any entry type..." below.
Windows has no equivalent trigger today (no browser extension, no
window-content visibility) and is explicitly deferred — see "Deferred:
Windows" at the end.

## The flow

1. **Trigger.** The user is on a signup field on some app or site's page and
   invokes account creation from the IME — the redesigned "+" key (see
   "What 'inside the IME' means" below). Detection (next) *biases* this
   quietly; it never pops up a suggestion on its own.
2. **Detect, best-effort.** Android hands every IME's `onStartInputView` an
   `EditorInfo` for the focused field — `autofillHints` (a field can be
   marked `NEW_PASSWORD` vs. plain `PASSWORD` by the page/app itself) and
   `packageName` (which app is focused). Today's `VaultIme.kt` reads
   neither. This feature starts reading both: `NEW_PASSWORD` nudges the "+"
   flow to open straight into creation mode instead of search, and
   `packageName` seeds a title guess for a native app's own signup screen
   (`PackageManager` can resolve a friendly label for it). Neither signal is
   reliable — plenty of forms don't set the hint, and a browser tab's
   `packageName` is just "Chrome" — so both are quiet defaults, never a
   requirement or a popup.
3. **Generate.** Reuses `generatePassword()` (`crypto/generator.ts`)
   unchanged — same defaults, same options panel, nothing new here.
4. **Fill.** Typed into the focused field via the same `InputConnection`
   mechanism the existing fill flow already uses.
5. **Capture, from *existing* entries only.** This was the one real fork in
   this design — see "Two ways to read 'fill in stuff while creating'"
   below. Settled answer: the creation panel lists the draft's Login fields
   (Username / Email / Password / URL / Notes), and for each, the user
   either generates (password only) or searches an *already-saved* entry and
   Fills its value in — the exact same pick-and-fill mechanism
   `PickEntryDetail`/the IME's search already has, just pointed at the
   in-progress draft instead of a finished one. Nothing new gets typed
   through the IME as a general keyboard; letter keys still only ever drive
   the existing search box.
6. **Confirm-password, for free.** A second password field on the signup
   form is handled by re-invoking Fill on the draft's already-set Password
   row — that retypes the same stored value, identically to how Fill on any
   saved entry's field already behaves. No special-cased "remember what I
   just generated" logic needed.
7. **Commit.** Exactly once, either when the user taps "Done" in the IME or
   when the vault locks (see "Session lifetime" below) — not after every
   field. One `Vault.addEntry` call with whatever fields were filled by
   then, immediately followed by `Vault.setNeedsReview(id, true)`. There is
   no "clean" commit path: every entry born this way starts flagged for
   review, regardless of which of the two triggers ended the session.
8. **Review.** The entry shows up pinned under "Review" at the top of
   `EntryList` (built — see below). Opening it and using the entry editor's
   ordinary Save button clears the flag automatically — no separate "mark
   reviewed" action exists or is needed.

## Two ways to read "fill in stuff while creating" — and why (a) won

**(a) — chosen.** The IME's creation panel is pick-and-fill against
*already-saved* entries, reusing 100% of the existing fill mechanism.
Zero new keystroke handling.

**(b) — rejected for now.** The IME becomes a genuine second keyboard
while creating: letters typed while, say, an email field is focused get
typed into that field *and* mirrored live into the draft. This would need
guessing which field is currently focused from `inputType`/hints,
rerouting letter keys away from the search box into direct typing, and
keeping a buffer in sync with whatever the user types by hand — real,
novel Android input-method plumbing, not a small add. Nothing here rules
it out later; it just isn't what got built.

## Data model

`Vault.setNeedsReview(id, needsReview)` (built, in `vault/vault.ts`) sets or
clears a `ph:review` field directly — deliberately outside
`EntryInput`/`applyInput`'s scheme. `applyInput` already wipes every
`ph:`-prefixed key on *any* ordinary edit and rewrites only what it's
explicitly given (see its own comment in `vault.ts`), so a key that's in
`isVaultFieldName` (it is — `fieldKeys.ts`) but that ordinary edits
never rewrite disappears on its own the next time the entry is saved
normally. That's the entire mechanism behind "opening it and hitting Save
clears the flag" — no code anywhere has to know that's what it's doing.

`VaultEntry.needsReview: boolean` (built, in `vault/types.ts`) surfaces it
to the UI, read in `Vault`'s `toVaultEntry`.

## Session lifetime

The in-progress draft (which fields have been filled, the generated
password) lives in memory in the JS/webview layer — the same place
`generatePassword()` and every other crypto/vault operation already live,
not duplicated into Kotlin. Nothing is written to the vault until it
commits. Confirmed behavior:

- **Survives switching apps.** Grabbing an SMS OTP mid-signup and coming
  back doesn't end the session. Only an explicit "Done"/cancel in the IME,
  or a lock, ends it.
- **Locking finalizes it.** `Vault.lock()` already runs in the JS layer, so
  hooking "commit whatever the draft has, flagged for review" into it is a
  direct addition there — not a new cross-process signal from Kotlin.
- **No periodic/incremental writes.** One `addEntry` + one `setNeedsReview`
  call, at whichever of the two triggers happens first.

## `EntryList`'s "Review" section (built)

A `needsReview` entry is pulled out of its normal category and pinned in
its own "Review" group, first, above the regular category list — same
reasoning as an "Overdue" bucket would get in the Upcoming tab: the thing
that needs a look shouldn't be sitting wherever it'd alphabetically land.
Only affects the grouped (not-searching) view; typing in the search box
finds a review entry like any other; the split doesn't apply there.

The IME's "+" key is what produces a `needsReview` entry now — see "The
Android side (built)" below.

## The Android side (built)

- `store.tsx`: `VaultCreateBridge`, installed as
  `window.__vaultCreate` the same way `window.__vaultFill` was
  — `startDraft`, `getDraft`, `generateDraftPassword`, `setDraftField`,
  `commitDraft`, `cancelDraft`. The draft itself lives in `draftRef`, a
  plain ref, for the same DevTools-hygiene reason `vaultRef` does.
  `commitDraftNow` writes straight to the vault (bypassing the `addEntry`
  action) so `commitDraft` can answer synchronously, and `lock()` calls the
  same function before nulling `vaultRef` — see that callback's own
  comment. `VaultScreen.tsx`'s old `window.__passHandlerNewEntry` (the "+"
  key's previous, `MainActivity`-launching behaviour) is gone; nothing
  replaces it there, since creation no longer leaves the IME.
- `WebViewBridge.kt`: `startDraft`/`getDraft`/`generateDraftPassword`/
  `setDraftField`/`commitDraft`/`cancelDraft`, thin `evaluateJavascript`
  pass-throughs to the bridge above, plus a `DraftLogin` data class
  mirroring `DraftLoginState`. `jsStringLiteral` — previously only ever
  handed entry IDs — was hardened into a real general-purpose JS-string
  escape (it now also carries arbitrary field values and picked entry
  text), including the two JS line-terminator characters (U+2028/U+2029)
  that a narrow backslash/quote escape would have missed.
- `VaultIme.kt`: reads this show's `EditorInfo` in
  `onStartInputView` and resolves a title guess (the focused app's
  `PackageManager` label, skipped for a known list of browser packages —
  see `KNOWN_BROWSER_PACKAGES`) and a "looks like a signup field" boolean
  (`autofillHints` containing `NEW_PASSWORD`/`PASSWORD`), handed to
  `keyboardView.setDetectedContext`. `MainActivity`'s old
  `EXTRA_LAUNCHED_FOR_NEW_ENTRY` launch path and `WebViewBridge.startNewEntry`
  are both gone — the "+" key never leaves the IME any more.
- `VaultKeyboardView.kt`: `showingDetail: Boolean` became a three-way
  `Screen { SEARCH, DETAIL, CREATE }`. "+" (`onPlusKeyTapped`) starts or
  resumes a draft and switches to `Screen.CREATE`, replacing the old
  "launch `MainActivity`" behaviour entirely. The creation panel
  (`buildCreatePanel`/`buildDraftFieldRow`) lists Username/Email/Password/
  URL/Notes; Password gets "Generate" (`generateDraftPasswordField`),
  every other field gets "Pick from Vault" (as first built — since narrowed
  to Email only and turned into an inline list, see the final revision;
  renamed from "Search" in a
  later color-scheme pass — `startPickingForDraftField`, which
  reuses the *same* search/detail flow as an ordinary fill — see
  `pickingForDraftField` and `finishFill`'s doc for how a pick started
  this way routes back to the panel instead of staying on the picked
  entry); any field with a value also gets "Fill", to retype it again —
  the confirm-password case is just tapping this a second time. The bottom
  keypad row swaps between `spaceRow`/`detailActionsRow`/`createActionsRow`
  (Lock/Cancel/Done) via `updateBottomRowsForScreen`, and a draft in
  progress survives a keyboard dismiss/reopen (`start()` re-fetches it and
  reopens straight into `Screen.CREATE` if one exists) — matching the
  design's "survives switching apps" requirement.
- `VaultImePreviewActivity.kt`: `FakePreviewEntrySource` grew a fake
  in-memory draft implementing the same functions, so the creation panel
  previews correctly without a real vault. Now that the flow isn't
  Login-only (see "Revision: any entry type..." below), it also carries a
  small canned `FAKE_ENTRY_TYPES`/`fakeDraftFields` table — not the real
  `entryTypes.ts` registry (this file has no access to it), just enough
  variety to preview the Type row actually changing what's below it.

## Revision: any entry type, and a narrower/dropdown Pick from Vault

Two changes on top of the Login-only version above — both direct requests,
both confined to the JS/Kotlin bridge and the Kotlin panel; nothing in
"The flow" or "Two ways to read..." above changed in substance, and the
vault layer needed no changes at all.

*(Superseded in its Kotlin specifics: the dropdown is now an inline list, not
a `PopupMenu`, and this paragraph's claim that the search detour was "deleted
outright" was untrue of the code as it stood — see the final revision below.)*

**"Pick from Vault" narrowed to Email, and became a dropdown.** Every
non-Password field used to get "Pick from Vault," which handed off to the
ordinary search-screen-and-detail-view flow (`startPickingForDraftField` →
`Screen.SEARCH` → `Screen.DETAIL` → `finishFill`'s `forDraftKey` branch).
Per direct request, that's gone: "Pick from Vault" now shows only on an
email-shaped field (`isEmailFieldName`, `vault/emailSuggestions.ts` — the
same check the app's own email-suggestion dropdown already uses), and
tapping it opens a `PopupMenu` of every distinct email-shaped value
already in the vault (`collectKnownEmails`, that same file) right there on
the panel, instead of leaving it for a separate screen
(`showEmailVaultPicker` in `VaultKeyboardView.kt`). Every other
field that used to get "Pick from Vault" (Username, URL, Notes, and — now
that this is generic — any other type's own template fields) simply has
no populate action beyond Grab/Fill any more; nothing replaces it. The old
search-screen detour (`pickingForDraftField`, `startPickingForDraftField`,
`finishFill`'s `forDraftKey` parameter) is deleted outright, not left
dead — nothing calls it any more now that Email is a dropdown and no other
field ever picked this way.

**Any entry type, not just Login.** The panel's header grew a "Type" row
(`buildDraftTypeRow`), defaulting to Login, with a "Change" action that
opens a `PopupMenu` of every type in `entryTypes.ts`'s registry
(`listEntryTypes`). Picking one (`setDraftType`) resets every field back
to blank — kept to that one simple rule rather than trying to carry a
value across two types' unrelated fields (even a same-named one:
`password` means the same *slot* on both `login` and `wifi`, but not the
same *thing* to a user re-reading the panel a moment later) — and keeps
only `title`, which has no type-specific meaning.

The draft itself generalized from a fixed Login shape
(`title`/`username`/`email`/`password`/`url`/`notes`) to `type` + `title`
+ a `fields: Record<string, string>` map (`DraftState`/`DraftSnapshot` in
`store.tsx`), keyed exactly like `EntryEditor.tsx`'s own `isLogin ? [] :
[...typeDef.templateFields, NOTES_FIELD]` split (`draftFieldDefsForType`)
— Login keeps its fixed five fields (still on KeePass's standard scheme,
see `vault.ts`), every other type reads its fields straight from the
registry, so this can never show a field the app's own editor wouldn't.
Committing a non-Login draft calls `Vault.addEntry` with `fields:
EntryFieldInput[]` instead of the flat Login properties — `EntryInput`
already supported this for every type-that-isn't-Login before this
change; nothing in the vault layer needed to move.

Which field gets which action generalizes with almost no new rules:
"Generate" is still exactly `key === 'password'` (the one key, across
every type in the registry, whose value is meaningfully "a random secret
that still works" — a generated Card CVV or license key would not be),
and "Pick from Vault" is the email check above. Both are resolved once,
on the JS side (`draftSnapshot`'s `canGenerate`/`canPickFromVault`), and
sent down as plain booleans — the Kotlin panel never has to know a
field's semantics itself, the same "TS is the source of truth" split the
rest of this bridge already follows for `FillField`/`listEntries`.

Not done as part of this pass: no attempt to give a non-text `dataType`
(`date`, `monthYear`) its own input affordance in the panel — every
field, regardless of type, is still populated via
Generate/Grab/Pick-from-Vault/Fill only, exactly like Login's fields
always were, never typed in directly (see "Two ways to read..." above,
still true). A `monthYear` Expiry field on a Card draft, say, can only
ever be Grabbed from the host field or left blank — there's no "Generate
a plausible expiry" or type-aware formatting here.

## Revision: generator options, and a way to actually see the password

One more direct request on top of "any entry type" above: the Password
field's "Generate" pill always used the app's own `DEFAULT_OPTIONS`
(length 20, every character class on) with no way to change that from the
keyboard, and every sensitive draft field — Password included — showed
nothing but "••••" once it had a value, with no way to check what had
actually been generated or typed. Both are fixed now, and both stay
confined to the same JS/Kotlin bridge and Kotlin panel as the revision
above — nothing in the vault layer or "The flow" changed again.

*(Superseded in part: the panel now also has a "Done" that collapses it and a
strength bar, and its layout/styling are pinned down — see the final revision
below. The "nothing collapses the panel" statement here no longer holds.)*

**The Options panel.** The Password field's "Generate" pill now expands
`buildPasswordOptionsPanel` directly below the row the first time it
actually produces a password — the same length range (8–64) and the same
four character-class toggles (`A-Z`/`a-z`/`0-9`/`!@#`) the app's own
`PasswordField.tsx`/`GeneratorPanel` shows, not a curated subset, plus its
own "Regenerate." There is deliberately no separate "Options" toggle —
an earlier pass in this same revision had one, but per direct follow-up
request it's gone: "Generate" both generates *and* reveals the settings
for what it just generated, and nothing collapses the panel again once
it's up (there is nothing else left to toggle it). Every control in the
panel is also a regenerate: dragging the length `SeekBar` or toggling a
class both call the new `setDraftPasswordOptions(options)` bridge method,
which persists the settings AND immediately produces (and types in) a
fresh password from them — mirroring the web panel's own `onChange` →
`regenerate(next, false)` behavior. The one deliberate divergence: the web
panel regenerates on every drag tick of its `<input type=range>`, cheap
since it never leaves the page; the IME only commits on
`onStopTrackingTouch` (finger lift) — a JS round trip per pixel of drag
over `evaluateJavascript` would be wasteful, and would retype the host
field many times over a single drag gesture. The last-enabled character
class still can't be turned off, mirroring `crypto/generator.ts`'s
`canDisable` (checked in Kotlin so the button is simply locked;
`setDraftPasswordOptions` also refuses an all-disabled combination as a
backstop, but that path should never actually be exercised in practice).

`passwordOptions: GeneratorOptions` lives on `DraftState`/`DraftSnapshot`
now, starting at `DEFAULT_OPTIONS` and resetting there on every
`emptyDraft` call — a type switch included, same "nothing but the title
carries over" rule the rest of the draft already follows.
`generateDraftPassword` (the plain "Generate"/"Regenerate" action) now
reads the draft's own stored options instead of always `DEFAULT_OPTIONS`.

**Replace, not append, on (re)generate.** A real bug caught in the same
follow-up: `onCommitText` is a thin `InputConnection.commitText(text, 1)`
call, which only ever inserts at the cursor — it never clears what's
already there first. That's fine for an ordinary Fill into an empty
field, but Generate/Regenerate is meant to be tapped repeatedly on the
*same* field as someone iterates toward a password they like, and each
tap was landing its new password right after the previous one instead of
replacing it. Both `generateDraftPasswordField` and `applyPasswordOptions`
now call the existing `onClearField()` (the "fix a mistake" key's own
callback — a generous `deleteSurroundingText` in both directions around
the cursor, same mechanism already used for the top-bar Clear key)
immediately before `onCommitText`, so every (re)generate replaces the
field's contents outright. Deliberately scoped to just these two
functions — Fill/Grab/Pick-from-Vault weren't reported broken and don't
share Generate's "tap the same field repeatedly" pattern, so they're
untouched.

**Show/Hide for every sensitive draft field.** Previously there was no way
to reveal what a sensitive draft field actually held — not just Password;
any sensitive field, on any type. Now `buildDraftFieldRow` grows a
"Show"/"Hide" pill (first in the action row, mirroring
`buildDetailFieldRow`'s own ordering) whenever a sensitive field has a
value. Deliberately **not** the same mechanism as `buildDetailFieldRow`'s
own reveal, though, despite living in the same file: that one
(`toggleReveal`/`revealedFields`) fetches an already-*saved* entry's
plaintext on demand and auto-hides again after `REVEAL_SECONDS` — the same
shoulder-surf guard the web app's `useReveal` hook gives `EntryDetail.tsx`/
`PickEntryDetail.tsx`. A draft field is different on both counts: its
plaintext is already in hand (`DraftFieldSnapshot.value` is always real —
see that class's own doc), so there's nothing to fetch, and the relevant
precedent isn't "viewing an already-saved entry" but "actively editing one
that isn't saved yet" — which on the web side (`PasswordField.tsx`'s own
reveal toggle, and `EntryEditor.tsx`'s plain reveal-toggle input for every
other sensitive field) has no timeout at all. So the new
`revealedDraftFields` (a plain `Set<String>` of currently-shown field
keys — no cached value needed, unlike `revealedFields`) has no timeout
either — cleared wherever a draft session ends or restarts (`start()`, a
type switch, `finishDraft`, `cancelDraftFlow`) for ordinary state hygiene,
not as a security measure.

Not done as part of this pass: the Options panel's length control is a
`SeekBar`, not a pixel-for-pixel port of the web panel's `<input
type=range>` — this file had no other draggable-slider precedent to
follow, so this is the first, and a few visual specifics (thumb size,
track styling beyond the `CREATE_ACCENT` tint) are whatever the platform
widget gives by default rather than a hand-matched copy of the web
control.

## Revision: inline email list and the full generator panel

**Status: built, not compiler-verified.** Kotlin in `VaultKeyboardView.kt`
(`buildEmailListPanel`, `buildPasswordOptionsPanel`, `buildStrengthBar`,
`createToggleChip`, `openDraftPanelKey` and friends), `WebViewBridge.kt`
(`PasswordStrength`) and `VaultImePreviewActivity.kt` (canned emails, fake
strength); JS side: `passwordStrength` on `draftSnapshot` in
`vault/accountCreationDraft.ts`, with a test. Same "not compiler-verified"
caveat as the rest of this document — a real Android build is what's left.
Still missing from the panel, unchanged by this revision: the Type row
(`buildDraftTypeRow`) and the Show/Hide pill for sensitive draft fields
(`revealedDraftFields`), both described as built above but absent from the
Kotlin.

Two direct bug reports against the IME's creation panel: the Email field's
"Pick from Vault" opens the entry *search* instead of offering emails already
saved in the vault, and "Generate" shows none of the generator UI the main
app's password field has. Both traced to lost Kotlin (see the status notes at
the top); this section is the agreed design for putting them back, settled
question by question before any code.

**Email: an inline list, not a `PopupMenu` and not the search flow.**
- "Pick from Vault" still shows only on email-shaped fields
  (`canPickFromVault`, from `isEmailFieldName`). Tapping it expands a list
  directly under the Email row; tapping it again collapses the list.
- Contents: `entrySource.listKnownEmails` — every distinct email-shaped
  value on any field of any entry (`collectKnownEmails`, see
  `docs/email-suggestions-design.md`), newest first. The full set: no filter
  box and no cap on how many. Roughly four rows are visible, then the list
  scrolls inside itself, so one long list can't take over the panel.
- Tapping an email **replaces** whatever is in the host field (clear, then
  type — the same `onClearField` + `onCommitText` pair "Generate" uses;
  appending would corrupt a half-typed address), records it in the draft
  (`setDraftField`), and collapses the list.
- No saved emails: the pill stays and the list shows one muted row, "No saved
  emails yet" — hiding the button would read as a bug.
- Why inline: a native `PopupMenu` is themed by the system (ignores the coral
  palette), can misplace or misbehave when launched from inside an
  input-method window, and wouldn't match the password panel's
  expand-downward behaviour. Rows are flat on the panel background,
  `CREATE_FG` text, thin dividers, no gradients.
- The old search detour is **deleted for real** this time: the
  `startPickingForDraftField` function, the `pickingForDraftField` state and
  every reference to it (`start()`'s reset, `renderResultsArea`'s stale-entry
  guard, the back-button/"New search" handling), and `finishFill`/
  `performFill`/`performExpiryFill`'s `forDraftKey` parameter and draft
  branch. Nothing in the Windows app or `PickEntryDetail.tsx` is affected —
  that is a different flow.

**Password: the whole generator panel, expanding downward.**
- "Generate" expands the panel directly under the Password row *and*
  generates, as the web dice button does (`setShowGenerator(true)` +
  `regenerate`). The panel is `buildPasswordOptionsPanel`, a port of
  `GeneratorPanel` in `src/ui/components/PasswordField.tsx`: a "Generator"
  heading with a **"Done"** that collapses it (the web has one; the earlier
  IME design's "nothing collapses it" is reversed), the length slider
  (`MIN_LENGTH`–`MAX_LENGTH`, 8–64) with its current value, the four class
  toggles (A-Z, a-z, 0-9, !@#) and "Regenerate".
- Any slider or toggle change regenerates via `setDraftPasswordOptions`,
  replacing the host field's text (clear, then type). The slider commits on
  finger lift, not per drag tick — unchanged from the earlier design and for
  the same reason (a JS round trip and a host-field retype per pixel is
  wasteful). The last enabled class can't be turned off (`canDisable`): its
  toggle is dimmed and unclickable.
- A **strength bar** (the web `StrengthBar`: five segments plus a label, red /
  amber / green tones, green reusing `SUCCESS`) shows under the Password row
  whenever the field has a value. The score and label come from
  `estimateStrength` on the JS side and travel down in the draft snapshot,
  the same "TS is the source of truth" rule the bridge already follows —
  the Kotlin panel does not reimplement the estimator.
- **No scramble animation.** The web field's 1.5s character shuffle is
  skipped: here the value is retyped into the *host app's* field, where
  flickering characters would be wrong, not a nicety.
- Styling stays in the coral palette. Toggles: on = the coral gradient pill
  (same as "Generate") with dark text; off = outline only in `CREATE_BORDER`
  with muted text. Slider: coral-tinted track and thumb. "Regenerate": the
  existing `createPillButton`.

**Layout: fixed height, scrolling.** `CREATE_HEIGHT_DP` (340) stays. The
opened panel (~150dp for the password one) pushes the rows below it down, and
the results region scrolls, auto-scrolling so the newly opened panel is fully
in view. The keyboard does *not* grow taller: that would resize the host app's
window and shift the very field being typed into on every open and close.

**State.** Only one of the two panels is open at a time — opening one closes
the other. Both collapse when the picker restarts (`start()`), the entry type
changes, or the draft is finished or cancelled — the same reset points as
`revealedDraftFields`. The password options themselves (length, class
toggles) live on the draft, so they survive re-renders and an app switch;
open-or-closed is plain view state and does not.

**Preview harness.** `VaultImePreviewActivity`'s fake source gets a canned
known-emails list and working options/strength values, so both UIs can be
eyeballed without a vault.

## Deferred: Windows

No browser extension exists in this project, and there's no window-title
or URL visibility today — so there's no reliable "you're on a signup page"
signal to act on, and no natural place to put a "+"-equivalent inside the
existing hotkey/search flow without one. Revisit once the Android half is
built and the shape of "detect → capture → commit → review" has proven
out; Windows would likely reuse the same commit/review pieces (they're
platform-agnostic) and only need its own trigger/detection story.
